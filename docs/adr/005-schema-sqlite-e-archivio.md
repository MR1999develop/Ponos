# 005. SQLite schema and archive of the original files

- Status: Accepted
- Date: 2026-11-05

## Context

Phase 1 fixes the format the user finds on disk: the database schema and the
way FIT and GPX files are kept. After release both are hard to change.

This ADR refines ADR 003 and replaces two of its parts: the file path
(`fit/<year>/<activity_id>.fit`) and the identity, which now also applies to
GPX files. The rest of ADR 003 remains valid.

Constraints:

- the original files are the source of truth; the database is an index and the
  user's data, and derived values are regenerated;
- the same activity must not enter twice, from any origin and in any format;
- no external data enters a file name or a query;
- a crash must not leave a record without a file or a half-written file.

## Options

### Database schema

1. **Tables with typed columns, `STRICT`, `CHECK` constraints equal to the
   domain invariants.**
   - Pro: the database rejects impossible data even if the code is wrong;
     queries by date, sport and distance are simple (phase 9).
   - Con: every change of shape requires a migration; the `CHECK`s must be
     kept aligned with the domain enums.
2. **One row per activity with a JSON document.**
   - Pro: no migration to add a field.
   - Con: no constraints or indexes on the fields; impossible values get
     through; queries on the content are slow and fragile.
3. **Schema generated by an ORM.**
   - Pro: less hand-written code.
   - Con: an extra dependency on the saved format; constraints and migrations
     not controlled; the on-disk shape depends on the library version.

### Name and location of the original files

1. **`archivio/<year>/<sha256>.<fit|gpx>`, everything generated by the
   program.**
   - Pro: no external data in the name; same content, same name (the write is
     idempotent); integrity is checked with the name itself; the year limits
     the number of files per folder.
   - Con: the name says nothing to the user; the year is that of the start and
     a file with a wrong start ends up in the wrong year.
2. **Name from the activity id (as in ADR 003).**
   - Pro: readable name.
   - Con: the identity is needed before writing; the Garmin id is missing for
     imported files; an external id in the name is untrusted data in a path.
3. **Original file name.**
   - Pro: recognisable to the user.
   - Con: Windows reserved names, long paths, collisions, `..`: all the
     security problems of paths.
4. **A single flat folder with the hash.**
   - Pro: simpler.
   - Con: up to 50,000 files in one folder; listing and backup slower.

### Identity of the activity

1. **FIT: `file_id` of the file. GPX: SHA-256 of the bytes. Duplicates between
   formats recognised by start and duration.**
   - Pro: the same FIT downloaded or copied from the watch has the same
     identity; the GPX, which has no `file_id`, still has a stable identity.
   - Con: the same activity as FIT and as GPX has two identities; the
     comparison by start and duration can be wrong (two almost equal
     activities, only one real).
2. **SHA-256 for all.**
   - Pro: a single rule.
   - Con: the same re-exported FIT has a different hash and enters twice.
3. **Only start and duration for all.**
   - Pro: does not depend on the format.
   - Con: false duplicates (two sessions close together) that delete real
     data.

## Decision

### Schema v1

- File `ponos.sqlite3`. On every connection: `foreign_keys = ON`,
  `trusted_schema = OFF`, WAL, `synchronous = FULL`, lock wait of 5 s.
- The version is only in `PRAGMA user_version`; v1 is 1.
- Tables, all `STRICT`:
  - `meta(key, value)`: `profile_id`, `name`, `timezone`; unknown keys are
    kept.
  - `activities`: one row per activity, with unique `identity_key` and
    `garmin_activity_id`, sport and format in closed sets, elapsed and moving
    time in seconds (`timer_s <= elapsed_s`), distance, ascent, optional start
    point and simplified track, relative path, SHA-256 and size of the
    archived file, origin and import instant. Index on
    `(start_ms, identity_key)`.
  - `physiology`: parameters valid from an ISO date (primary key).
  - `load_cache`: one load per activity, with the fingerprint of the
    parameters; derived, it is deleted with the activity and regenerated.
- Times are integers in UTC milliseconds (`start_ms`, `imported_ms`). Measured
  durations stay in seconds (`REAL`).
- Columns and constraints are in `storage/sqlite_schema.py`, which is the
  single source: this ADR does not repeat them.

### Migrations

- A migration is a list of statements, run in a single transaction; never
  `executescript`. A migration already released is not modified: another one
  is added.
- Before every migration the app copies the database into `backup/`.
- A database of a version newer than the known one is rejected without
  touching it. A file without a schema or one that does not pass `quick_check`
  and `foreign_key_check` is reported as damaged.
- A test compares the closed sets of v1 with the domain enums: a new value
  forces a migration to be written.

### Archive

- Path `archivio/<year>/<sha256>.<fit|gpx>`; the year is that of the start in
  UTC. The path is made only of the characters `A-Za-z0-9._-`.
- Write: temporary file created exclusively in the year folder, `fsync`, rename
  to the final name, then synchronisation of the folder where the system
  allows it. The SQLite record is written after the file, in the same
  transaction as the duplicate check. A crash leaves at most an orphan
  temporary file, removed at start-up.
- Durable file replacements go through a single shared module.
- The archive inherits the private permissions of the profile folder.
- Saving the same bytes twice writes nothing. If the file is there but the
  bytes do not match the name, it is replaced atomically with the right ones
  (this is the "repaired" case of the import).
- Every read verifies size and SHA-256; an altered file is reported, never used
  silently. No link is followed.

### Identity and duplicates

- FIT: identity from the `file_id` (manufacturer, product, serial number, UTC
  creation time). GPX: SHA-256 of the bytes. Saved text key: `fit:<...>` or
  `gpx:<sha256>`.
- Same activity in two formats: possible duplicate if the starts are at most
  60 s apart and the durations differ by at most 5% (project default). The
  first to arrive is kept.
- Format recognised from the content and consistent with the extension.

## Consequences

- The folder stays self-sufficient. ADR 003 keeps its validity except for the
  file path and the identity of GPX files.
- The file name says nothing to the user; the app is needed to open an
  activity.
- A database can have stricter constraints than the code: a bug that writes
  impossible data fails visibly.
- Every schema change requires a migration, the safety copy and a test on the
  database of the previous version.
- A change of the archive path or of the identity requires a new ADR.
- The comparison by start and duration may fail to recognise a duplicate
  outside the threshold: the activity enters twice. Accepted; the user loses no
  data.

## How compliance is verified

- T-DATI-01: a test database for every version, brought to the latest; future
  version rejected; safety copy created.
- T-DATI-02: interruption at every point of the write, with a file system
  adapter that fails at the N-th operation.
- T-DATI-03: archived file altered or missing, reported and repaired by the new
  import.
- T-IMP-03 and T-GPX-02: idempotence and duplicates between FIT and GPX in any
  order.
- T-SEC-04: no external data in the archive names. T-SEC-05: no composed SQL.
  T-SEC-09: private permissions.
- Contract tests in `tests/contracts/` for the `ActivityArchive` and
  `ActivityIndex` ports, run on the fake and on the real adapter.
- The test on the closed sets of v1 (above) and `import-linter` in the CI.
