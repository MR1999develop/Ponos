# Deferred tidying

Code tidying that was put off: one entry per line, with date and reason.

- 2026-11-05: the charts page (`QWebEngineView`) may swallow the drag of files dropped on the chart; dragging works on the rest of the window. To check by hand and, if needed, intercept the drop at application level.
- 2026-11-06: an archive file with no record in the index (left after a failed commit, because the archive is written first and the record after) is neither picked up nor deleted. To reconcile with the synchronisation journal in phase 2.
- 2026-11-06: starting the web engine (Chromium: profile, page and view) costs about 180 ms in the UI thread and cannot be moved elsewhere. The window does it right after the first `show()` (`ChartView.start_engine`), not in the constructor and not at the first drawing; the acceptance test D-F1-10 measures responsiveness during the first drawing and prints the start-up time as phase `avvio_motore`. To be reconsidered only if Qt offers an asynchronous start. Measurement of 2026-11-06 (offscreen): first start about 185 ms, each additional view about 3 ms; postponing the start to the first need (start of the calculation or first drawing) would bring the 185 ms inside the import, over the limit of 100 ms per event (T-UI-02), and postponing only the two secondary views saves 6: left after the first `show()`.
- 2026-11-06: the UI tells the three failures of the profile list apart (future version, busy, corrupt) with `ErrorContext`/`RegistryProblem`, composed in `__main__`, because `RegistryFormatTooNewError`, `RegistryBusyError` and `RegistryCorruptError` are in `platform` (the UI cannot import it). Moving the three exceptions to `profiles.ports` (they are already subclasses of `ProfileRegistryError`) removes the detour.
- 2026-11-06: the web engine is torn down explicitly: `ChartEngine.dispose` (from the first `closeEvent` of the window and from `aboutToQuit`) destroys the pages of the registered views at once and then the profile, so the order does not depend on that of the Qt children (`keep_last` no longer exists). Consequence: if the two-step close times out and the window stays open, the charts are already empty. To be reconsidered only if that case becomes common.
- 2026-11-06: a run of `tests/ui` hung once during the fixes to the two-step close and did not reproduce in 8 runs with `faulthandler`; keep an eye on the CI and, if it happens again, rerun with `faulthandler` and a timeout per test.
- 2026-11-06: the typed password reaches `GarminAccount.login` as a Python `str`, which cannot be zeroed in memory: the dialog field is cleared at once and `Credentials` hides it in `repr`, but a copy stays until the garbage collector frees it. Accepted (the port asks for `str`); to review if Garmin offers a login without a password.
- 2026-11-06: during the first synchronisation (even thousands of activities) the table and the overview are updated only at the end of the run; the activities downloaded before an interruption appear in the next run or at the recalculation. Updating in groups (every N activities) is possible but must be measured first.
- 2026-11-06: the system notification (`platform/notifier.py` on `desktop-notifier`, in a thread of its own) is tested only with a fake sender; the real behaviour on Windows 10/11 (toast of an unregistered app) and on Ubuntu must be checked by hand in the phase 2 acceptance.
- 2026-11-06: the language chosen in the Language menu applies at the next start (a message says so). Retranslating on the fly with `LanguageChange` would force reassigning the texts of every window, menu, table header and chart (strings duplicated in two places) for an action done once; to reconsider if it must be changed often.
- 2026-11-06: the "Activity detail" window does not change theme on the fly if the system colour scheme changes while it is open (the overview does); the figure is redrawn when reopened.
- 2026-11-06: the three overview charts are in a vertical `QSplitter` (4:3:3) whose division is not remembered between starts; a tab or a scrollable panel would require letting the wheel pass through `QWebEngineView`, which today swallows it.
- 2026-11-06: height and weight are text fields (comma and decimal point in the weight, no proposed value); a numeric control with a special value would constrain more, but the date of birth is the only field that justifies it (`BirthDateEdit`).
- 2026-11-06: the "Edit profile" window recomputes the validity period itself (`MeasurementsForm.pending_periods`) with the rule of `UpdateMeasurements` ("until the day before the next entry"), which in the core is the private function `_period_in`. If the core exports it (for example as `ValidityPeriod.in_series`) the copy in the UI goes away.
- 2026-11-07: the calculation of a day (day page) cannot be cancelled once started, only dropped when the page is left (`NutritionLoader.cancel_day` ignores the answer): `run_on_profile` jobs do not receive a `JobContext`. A day reads at most a few FIT files, so there is no Stop; to be reconsidered if a day can take seconds.
- 2026-11-07: `main_window.py` is above 1100 lines. The calendar and nutrition commands (actions, menu, enabling rules) could move to a `CalendarUi`/menu builder like `GarminUi`, leaving the window with composition only.
- 2026-11-07: move `_build_actions` and `_build_menus` of `main_window.py` into a module of their own (an action and menu builder that receives the window's slots), so the window keeps composition and state; in a separate `tidy:` commit, with the tests green before and after.
- 2026-11-08: `garmin/connect.py` (`ConnectClient`) should check with `getattr` that each `garminconnect.Garmin` method exists before calling it, as `garmin/workouts.py` now does, so a library change is reported as unsupported rather than as a generic error.
- 2026-11-09: with FIT only, `FileFormat` has a single value: `format_of`, the "Format" column of the table, `file_format` of `Activity` and `ActivityRecord` (and the SQL column) and the `file_format` parameter of `decode_stored_activity` / `decode_stored_track` carry no information any more. Remove them together, with an expand-contract migration for the column, if a second format is no longer expected.
